# Design

## Context

Проект — одномодульное Go-приложение без внешних зависимостей. Шаблоны и статика вшиты через `//go:embed`
и парсятся в `NewServer` (`templates/*.html prompt.tmpl risks.tmpl static`). Существующий поток «Оценка
нейросетью» уже делает то, что нужно для уточнения шага: `GET /cases/{id}/prompt` собирает JSON-промпт
(`buildPrompt` + `prompt.tmpl`), `POST /cases/{id}/import` разбирает ответ (`parseAssistantReply`), превью и
`POST /cases/{id}/apply` применяют. Шаг — это `Step{ID, Title, Done}` внутри `Action.Steps`, порядок задаётся
порядком в слайсе. `newID("s")` даёт шагу уникальный id. Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Переиспользовать существующий паттерн «промпт → импорт → превью → применить» для шагов.
- Нумеровать шаги без миграции данных и без ручного переупорядочивания.
- Держать схему детализации отдельно от схемы оценки весов.

**Non-Goals:**
- Вызов нейросети напрямую (API) — вставка ответа остаётся ручной.
- Ручное переупорядочивание шагов (нумерация — производная, а не редактируемое поле).
- Выборочное применение части возвращённых под-шагов — применяются все.
- Изменение существующего поведения оценки весов.

## Decisions

**1. Номер шага — производный, не хранится.**
Позиция шага вычисляется как 1-based индекс в `Action.Steps` при отрисовке и при сборке селектора.
Альтернатива — поле `position int` в `Step` — отклонена: избыточно, требует миграции и рискует рассинхроном
с порядком слайса. Для идентификации шага в форме используется его `id`, а номер — только для показа и выбора.

**2. Селектор шагов — внутри каждого действия.**
Панель «Оценка нейросетью» переименовывается в `API AI` (в ней остаётся только поток оценки весов). Поток
«Уточнить шаг» живёт **внутри каждого действия** — отдельной сворачиваемой секцией после «изменить» и
«обоснование нейросети» (по уточнению пользователя: «уточнить шаг — после каждого шага, под изменить и
обоснование нейросети»). Селектор перечисляет шаги только этого действия как «шаг N: название», значение —
`actionID/stepID` (тот же контракт, что и у обработчиков). id элементов (`#refine-step-…`, `#refine-prompt-box-…`,
`#refine-result-…`) привязаны к id действия, чтобы не пересекаться на странице.

**3. Новый шаблон и новая схема ответа.**
Добавляется `refine.tmpl` и структуры `refineRequest` / `RefineReply` в prompt.go (или отдельный файл).
`RefineReply` содержит `action_id`, `step_id` и `steps []string` (под-шаги). Валидация повторяет дух
`Validate`: `action_id` и `step_id` должны совпадать с выбранными, список непустой, названия под-шагов
непустые. Промпт включает короткий контекст (кейс, действие) и короткий список шагов — как просил пользователь.

**4. Маршруты повторяют существующую тройку.**
- `GET /cases/{id}/refine/prompt?step=<stepID>` — сборка промпта уточнения.
- `POST /cases/{id}/refine/import` — разбор ответа и превью под-шагов.
- `POST /cases/{id}/refine/apply` — замена шага и перерисовка тела кейса.

**5. Замена шага.**
В `store.Update`: найти действие по `action_id`, шаг по `step_id`, удалить шаг (`slices.Replace`), вставить
на его индекс выбранные под-шаги (`Step{ID: newID("s"), Title: title}`, невыполненные). Выбор под-шагов —
через чекбоксы в превью (`name="keep"`, значение — индекс под-шага); если не отмечен ни один — ошибка без
изменений. Номера пересчитаются сами. Операция атомарна: любой сбой валидации до мутации.

**6. Панель API AI как `<details class="panel">`.**
Остаётся сворачиваемым блоком (как сейчас «Оценка нейросетью») и содержит только поток оценки весов.
Секция «Уточнить шаг» — обычная `inline-details` внутри действия. Минимум новых стилей: нумерация шага
(`.step-num`) и отступы.

**7. Взаимная несовместимость схем ответа.**
Оба импорта разбираются строго через `decodeReply` + `DisallowUnknownFields`. У оценки весов верхнеуровневые
поля — `case_id`/`actions`/`suggested_actions`/`comment`, у уточнения — `action_id`/`step_id`/`steps`; наборы
не пересекаются. Поэтому корректный ответ одной схемы, вставленный в другой поток, падает на неизвестном поле
до любой мутации данных. Это поведение закреплено требованием в спеке и проверяется в задачах.

## Risks / Trade-offs

- [Шаг `done`, который разбили] → под-шаги стартуют невыполненными, т.е. «выполнено» теряется. Осознанно:
  у грубого шага нет однозначного отображения на под-шаги; пользователь заново отмечает. Зафиксировано в спеке.
- [Номер шага меняется при вставке/удалении] → номер не является постоянным идентификатором; внутри селектора
  и форм всегда передаётся `id`. Риск только косметический (номер «плывёт»).
- [Ответ с посторонним текстом/```json фенсами] → переиспользуем `decodeReply` (берёт текст между первыми
  `{` и последними `}`), как в весах.
- [Два подблока в одной панели растут] → поток уточнения вынесен внутрь каждого действия, панель «API AI»
  держит только оценку весов.

## Migration Plan

Изменения затрагивают только код и встроенные шаблоны; миграции данных нет (номер — производный, под-шаги
создаются через `newID`). Развернуть: пересобрать `go build`, перезапустить сервер. Откат — обычный git-откат;
данные не затрагиваются до первого успешного «Применить» уточнение.
